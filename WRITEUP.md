# Wizardry Gold — Forcing a High Bonus Roll (Faery Ninja Fix)

## Goal

Create a **Faery Ninja** at character creation in *Wizardry 7: Crusaders of the
Dark Savant* (the "Wizardry Gold" Windows re-release, `WIZARD_720.EXE`). Faery
Ninja requires an improbably high character-creation **bonus-points roll**, so
the practical goal was: make the game produce a high roll on demand.

## TL;DR

The bonus roll is generated by code at virtual address `0x475962`. That routine
contains **dormant developer code**: if the flag word at `0x4A20A0` equals `1`,
it rolls `random(10) + 21` (i.e. **21–30**) instead of the normal ~5–11. The
shipped game forces that flag to `0`, so the branch never runs. The fix is a
**6-byte patch** that NOPs the conditional jump guarding the branch, so the
elite roll always fires. The roll is produced by the game's own code, so
profession eligibility (which is computed from the roll) sees a genuine high
value and Faery Ninja becomes selectable.

- File offset patched: `0x74E15`
- Original bytes: `0F 85 16 00 00 00`  (`jne 0x475A31`)
- Patched bytes:  `90 90 90 90 90 90`  (6× `nop`)

## Why the obvious approaches failed

The investigation started with a runtime memory tool (`wizgold_highroll.py`)
that located the bonus value and tried to edit it. Every value-editing approach
failed, for reasons that the disassembly later explained:

1. **One-shot write of the bonus value.** The value lives at a static address,
   `0x4A209C`. Writing a high number there changed the *displayed / spendable*
   number but **not** which professions were selectable.

2. **Pinning the value (continuous overwrite).** Same result. Eligibility never
   changed. Also revealed the value is re-rolled the instant you pick a gender —
   a pre-gender write is wiped by the fresh roll.

3. **Hardware-breakpoint injection.** Attaching a debugger, setting a hardware
   write-breakpoint on `0x4A209C`, and overwriting the value the moment the game
   wrote the roll — this **crashed the game**, because injecting mid-handler
   corrupted creation state (and the value is a 16-bit field, so a 4-byte write
   clobbered the neighbouring word at `0x4A20A0`).

The common root cause: **profession eligibility is computed from the roll at the
moment of the gender-click, and is never re-read from the editable value.** So
editing the value afterward is cosmetic. This was independently confirmed by
community sources (a Wizardry 7 FAQ: *"This bug doesn't help you roll elite
characters, since you can't raise the attribute points until after you've chosen
your profession"*).

Conclusion: you cannot win by editing the **value**. You have to change how the
**roll is generated**. That requires static analysis of the executable.

## Reverse engineering

### Tooling

- `analyze.py` — parses the PE headers of `WIZARD_720.EXE`, finds every
  occurrence of a 4-byte address constant in the code, and disassembles around
  each site (Capstone, 32-bit x86) to classify reads vs writes.
- `disasm_range.py` — linearly disassembles arbitrary virtual-address ranges.

PE layout (ImageBase `0x400000`):

| Section | VA start    | Raw ptr  | Notes                         |
|---------|-------------|----------|-------------------------------|
| `.text` | `0x401000`  | `0x400`  | code                          |
| `.data` | `0x49E000`  | `0x9BC00`| globals — includes `0x4A209C` |

VA → file-offset mapping (for `.text`):
`fileoff = 0x400 + (VA - 0x401000)`.

### The bonus field

References to `0x4A209C` showed it is read/written as a **`word` (16-bit)**:

```
mov   word ptr [0x4a209c], ax
movsx eax, word ptr [0x4a209c]
```

This explains the pre-roll reading of `0xFFFF` (65535) — it is an uninitialised
`-1` sentinel, set just before the roll.

### The roll generator (VA 0x475962), annotated

```asm
mov   word [0x4A209C], 0xFFFF      ; init bonus = -1 (sentinel)
; ...race/base-stat setup calls...
push  6
call  0x468233                     ; random(6) -> 0..5
movsx eax, ax
add   eax, 5                       ; -> 5..10
mov   word [0x4A209C], ax          ; BASE ROLL = 5..10

push  0x14
call  0x468233                     ; random(20)
test  eax, eax
jne   +                            ; 1/20 chance:
  add  word [0x4A209C], 8          ;   +8

push  0x14
call  0x468233                     ; random(20)
test  eax, eax
jne   +                            ; 1/20 chance:
  add  word [0x4A209C], 8          ;   +8

movsx eax, word [0x4A209C]
cmp   eax, 9
jge   +                            ; floor: if roll < 9,
  push 4
  call 0x468233                    ;   roll = random(4)+8  (9..11)
  add  eax, 8
  mov  word [0x4A209C], ax

; ---- dormant elite branch ----
movsx eax, word [0x4A20A0]         ; read the flag next to the bonus
cmp   eax, 1
jne   0x475A31                     ; <-- if flag != 1, SKIP elite roll
  push 0xA
  call 0x468233                    ;   random(10)
  add  eax, 0x15                   ;   + 21
  mov  word [0x4A209C], ax         ;   ELITE ROLL = 21..30
0x475A31:
; ...continues...
```

Normal output: base `random(6)+5` plus two rare `+8`s, floored to ≥9 → typically
**5–19**, clustered low. (Observed in testing: 8, 9, 10, 11.)

### The dormant elite branch

The block at `0x475A0B`–`0x475A2B` rolls **21–30** — but only if the `word` at
`0x4A20A0` equals `1`.

Searching every reference to `0x4A20A0` found exactly **two**:

1. `0x475A0B` — the read above (the elite trigger).
2. `0x476881` — `mov word [0x4A20A0], 0`, i.e. the game **forces the flag to 0**
   during creation setup.

Nothing in the binary ever sets it to `1`. The elite branch is effectively a
**developer / debug high-roll cheat that ships disabled**. This is why normal
play never produces 21–30, and why setting the flag at runtime is racy (the
setup code re-zeros it).

## The fix

Rather than fight the flag at runtime, neutralise the guard statically. The
conditional jump that skips the elite branch:

```
0x475A15:  0F 85 16 00 00 00   jne 0x475A31
```

Replacing it with six `nop`s makes control **always fall through** into the
`random(10)+21` block, so every roll is 21–30 regardless of the flag:

```
0x475A15:  90 90 90 90 90 90   nop ; nop ; nop ; nop ; nop ; nop
```

After the elite block writes the bonus, execution continues naturally at
`0x475A31`, so the patch is self-contained and changes nothing else.

### Why this is the right lever

- **No timing race.** The high value is produced by the game itself during
  generation, before eligibility is computed.
- **No crash.** No external memory writes during the creation handler; no
  clobbering of the adjacent `0x4A20A0` word.
- **Eligibility passes legitimately.** The profession list is built from the
  rolled total, which is now genuinely 21–30 — enough to clear Faery Ninja's
  attribute deficit (~22 points: Faery base vs Ninja minimums
  STR12/INT10/PIE10/VIT12/DEX12/SPD12).
- **It is the game's own code path**, not a fabricated value.

## Applying / reverting

`patch_wizgold.py`:

- `python patch_wizgold.py` — backs up to `WIZARD_720.EXE.bak`, verifies the
  exact original bytes at offset `0x74E15`, writes the 6 NOPs. Refuses to patch
  if the bytes don't match (wrong version) or the exe is locked (game running).
- `python patch_wizgold.py --revert` — restores the original bytes (from backup,
  or by rewriting them directly).
- `python patch_wizgold.py --status` — read-only state check.

Procedure:

1. Close Wizardry Gold (the exe is file-locked while running).
2. `python patch_wizgold.py`.
3. Launch, create: name → Faery → gender → bonus rolls **21–30** → pick **Faery
   Ninja** → allocate points → finish normally.
4. Optional: `python patch_wizgold.py --revert` to restore normal rolls.

Note: while patched, **every** character creation rolls 21–30, not only Faery.

## Addressing, ASLR, and portability

A natural question: are these addresses the same on every machine, or
machine-specific? They are **the same for everyone running the same build** —
and the reason is worth spelling out.

### Why the addresses are fixed

`WIZARD_720.EXE` is a 1990s 32-bit PE. Checking its PE optional header:

```
ImageBase:           0x00400000
DllCharacteristics:  0x0000
  DYNAMIC_BASE (ASLR, 0x40):  not set
  NX_COMPAT    (DEP,  0x100): not set
```

`DYNAMIC_BASE` is off, so the OS loads the image at its fixed preferred base
`0x400000` every time. **No ASLR.** Address Space Layout Randomization didn't
exist when this game was built, so it was never compiled in.

Consequences:

- Every global lives at a hardcoded virtual address: the bonus value at
  `0x4A209C`, the elite flag at `0x4A20A0`, the roll code at `0x4759xx`. These
  are identical on every launch and every machine for this binary. (This is why
  the original runtime tool re-found `0x4A209C` on every restart, and why a
  static patch is reliable rather than a lucky guess.)
- Contrast with a modern game: ASLR would slide the image to a random base each
  launch, so a *runtime* memory editor must re-locate addresses every time. A
  *file* patch to code still works there because it is file-relative — but here
  we get the best of both: fixed file offsets **and** fixed runtime addresses.

### Why the patch is portable (and safe when it isn't)

The patch is applied to **bytes in the exe file**, not a live address, so anyone
with the identical exe gets the identical result regardless of their hardware,
OS, or where Windows loads the process.

"Identical exe" is the key qualifier. A different revision (the DOS original, a
different Gold patch level, another distributor's build) could have different
code at different places. The patcher handles this defensively:

- It locates the patch site by **byte signature** — the guard instructions
  `movsx eax,[0x4A20A0]; cmp eax,1; jne` — not by a hardcoded offset. So the
  site is found even if it has shifted within a matching build, and the file
  offset (`0x74E15` for the analysed build) is derived, not assumed.
- It **verifies** the bytes before writing, and **refuses** with "signature not
  found / unsupported build" on anything it doesn't recognise, rather than
  blindly patching the wrong location and corrupting the exe.

Portability limit: the signature currently includes the absolute address
`0x4A20A0`, which is build-specific, so it matches exactly the analysed Gold
7.20 build. To cover structurally-identical variants, the four address bytes in
the signature could be wildcarded (match the `movsx`/`cmp`/`jne` opcodes while
skipping the operand) — the range-edit offsets (`+7`, `+0x15` from the `jne`)
stay valid because they are relative to the instruction stream, not the global.

## Verification

- Static: on-disk bytes at `0x74E15` confirmed `0F 85 16 00 00 00` before patch;
  patcher verifies before/after.
- Runtime: confirmed by the user — after patching, the gender-click roll lands in
  the 21–30 range and Faery Ninja is selectable at creation.

## Key addresses (reference)

| Address     | Meaning                                                      |
|-------------|-------------------------------------------------------------|
| `0x4A209C`  | Bonus-points value (16-bit `word`).                         |
| `0x4A20A0`  | Elite-roll flag (`word`); `1` ⇒ roll 21–30. Ships as `0`.   |
| `0x475962`  | Roll-generator routine entry-ish (init + base roll).        |
| `0x475A0B`  | Read of the elite flag.                                     |
| `0x475A15`  | The `jne` guarding the elite branch — **patched to NOPs**.  |
| `0x475A1B`  | Elite roll block: `random(10)+21`.                          |
| `0x475A1C`  | `push` immediate = roll **spread** (default `0x0A`=10); `jne`+7. |
| `0x475A2A`  | `add eax` immediate = roll **base** (default `0x15`=21); `jne`+0x15. |
| `0x468233`  | `random(n)` — `push n; call` returns `0..n-1`.              |
| `0x74E15`   | **File offset** of the patched `jne` (this build).          |

The roll range is `[base, base + spread - 1]`; the patcher's `--min/--max`
(and the GUI inputs) rewrite those two immediate bytes. Default = 21–30.
